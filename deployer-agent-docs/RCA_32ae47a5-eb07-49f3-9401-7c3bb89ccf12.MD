# RCA — safyra.co Cloudflare 520 on repeated/large HEIC uploads

## Problem statement
Cloudflare 520 ("Host Error", unknown connection between Cloudflare and origin) reproduced on https://safyra.co at ~2026-11-02 03:41 UTC while repeatedly uploading HEIC/HEIF (and mixed JPEG/PNG/WEBP) images via POST /api/media/upload in the admin product editor. Single uploads succeed (201, converted to JPEG); failures appear only after several large uploads in quick succession. Separate user report "iPhone HEIC/HEIF not uploading" is the same symptom (origin down/restarting → browser sees a failed network request, not a clean 4xx).

## Confirmed root cause (from prod events + logs, run 32ae47a5)

**1. Backend pod OOMKilled at the tier memory ceiling during HEIC processing.**
- get_pod_events: pod `...-62z9l` container `last terminated: OOMKilled (exit 137) at 2026-11-02T03:41:18Z, restarts=1` — exactly the reported window.
- get_tier: tier_0 "Starter", `memory_limit: 512Mi`, `cpu_limit: 250m`, replicas 2, HPA disabled (max_replicas 2). Full-resolution iPhone HEIC/ProRAW decode (12–48MP) + Pillow re-encode/optimize peaks well above 512Mi, so memory crosses the tier limit and the kernel OOM-kills the container.

**2. Heavy synchronous image work blocks the backend event loop → health probes fail → liveness restarts, independent of OOM.**
- nginx logs show repeated `upstream timed out (110) while reading response header from upstream ... "GET /health" ... 127.0.0.1:8001` at 03:39:03, 03:39:53, 03:40:39, 03:41:09, 03:41:13 — i.e. the backend stopped answering /health while busy decoding, BEFORE the OOM.
- After OOM: `connect() failed (111: Connection refused)` (03:41:22, 03:41:27) and Readiness/Liveness/Startup probe HTTP 503. This is when the origin returns 520 to Cloudflare / refuses connections.
- Same pattern of /health connection-refused + timeouts recurs across the day (00:17, 01:10, 02:22, 03:03, 03:16) — the backend is getting restarted by probe failures under load repeatedly, not only at 03:41.

## Why single uploads work but bursts fail
One upload fits within 512Mi and finishes before the liveness window elapses. Several large HEIC decodes in quick succession (concurrent requests on a single process, no concurrency cap, no downscale-before-decode, no memory bound) stack peak memory and block the event loop → OOMKill + probe-driven restart → origin unreachable → Cloudflare 520.

## Fixes
1. **User (tier_upgrade_needed):** Raise the deployment tier in Deployment Panel → Resources (e.g. tier_1/tier_2) to give the backend more than 512Mi memory headroom. This is the confirmed limit that triggered the OOMKill.
2. **Code (E1):** Make media upload processing bounded and non-blocking in backend/routers/media.py:
   - Run the CPU/memory-heavy Pillow decode/re-encode in a worker thread (e.g. `run_in_threadpool`/`asyncio.to_thread`) so it doesn't block the event loop and stall /health → stops liveness-probe restarts.
   - Downscale/limit max pixels before full re-encode (cap `Image.MAX_IMAGE_PIXELS` / enforce a max dimension; use draft/thumbnail for oversized source) to bound peak memory per request.
   - Add a server-side concurrency limit / semaphore for simultaneous image conversions and an explicit max upload size, returning a clean 413/429 instead of letting memory blow up.
   - Free buffers promptly (close PIL images, drop the raw bytes) after conversion.
   Tier headroom alone reduces OOMs but will not stop event-loop blocking / probe restarts without the code changes; both are needed for a robust fix.

## Not the cause
No application traceback/500s in logs (status mix was 200/201/404 only; the 404s are `GET /health` on the uvicorn app — handled by nginx, benign — and a few missing legacy media ids). No DNS/SSL/domain problem (both safyra.co and www verified). Not a secrets issue. The 520 is purely origin unavailability during OOM/restart.
