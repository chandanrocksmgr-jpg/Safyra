# RCA (follow-up) — safyra.co "IMG_8807.jpeg could not be uploaded" (job_id cbc3291b-01eb-4fc4-a20c-f6741812ed10)

**Deployment:** lucknowi-craft · live custom domain https://safyra.co · mobile Chrome
**Active run:** 4b02ba49-d2f3-442b-9fb4-539f21f1546b (success)
**Flow:** Admin → Products → Product gallery → Upload images → `POST /api/media/upload` (multipart, admin-cookie protected)

## Verdict
This is **NOT** a custom-domain routing / CDN / CORS / cookie(SameSite) problem. It is the **same backend HTTP 415 content-type rejection** from the earlier report, hidden behind a misleading frontend toast. The iPhone photo IMG_8807.jpeg is being rejected by the app because its real format is not JPG/PNG/WebP (HEIC/HEIF), and the UI shows a generic "could not be uploaded" message that makes it look like a network failure.

## Why the reporter's "network-level failure" read is wrong (PROVEN in source)
`frontend/src/components/ImageManager.tsx`, upload() catch block:
```js
toast.error(reason instanceof ApiError && reason.status === 413
  ? `${file.name} is too large even for a studio original`
  : `${file.name} could not be uploaded`);
```
The generic toast fires for EVERY error except an `ApiError` with `status === 413`. A clean backend **415 ApiError hits the generic branch** and prints exactly "IMG_8807.jpeg could not be uploaded". So this toast does NOT prove a network/CORS/no-HTTP-response failure — it is also what a normal 415 produces. (`api.ts:48-52` shows `apiUpload` throws `new ApiError(res.status, errBody)` on any non-OK response, so 415 becomes an ApiError.)

## Routing / CORS / cookie are healthy (PROVEN)
- Domains: `safyra.co` + `www.safyra.co` — verified, `ssl_status: active`, DNS linked (list_domains, check_domain_status). Provider Cloudflare.
- Backend access logs for the active run (last 240 min) show `POST /api/media/upload` returning **415 ×19 in bursts AND 201 Created** interleaved, plus `POST /api/products 201`, `GET /api/auth/me 200`, `GET /api/admin/order-alerts 200`. Requests arrive from the edge egress IP 136.68.30.50.
  - => multipart `/api/*` POSTs DO traverse safyra.co → Cloudflare → pod nginx → FastAPI. Routing works.
  - => A 415 is returned only AFTER `require_admin` passes (bad/missing admin cookie would be 401/403, not 415). So the httpOnly admin session cookie IS being forwarded correctly on safyra.co. No CORS/SameSite/cookie break.
- Single phone photos are a few MB, far under the 100M nginx / Cloudflare body caps — body-size limits are not in play here.

## Root cause (PROVEN) — backend 415 on an iPhone HEIC photo
`backend/routers/media.py`:
- L23 `ALLOWED_TYPES = {image/jpeg, image/png, image/webp}`
- L67-68: content_type not allowed → 415 "Upload a JPG, PNG or WebP image"
- L79-82: PIL can't decode (HEIC without pillow-heif) → 415 "The file is not a valid JPG, PNG or WebP image"
- L84-85: detected format ≠ declared content_type → 415 "The image format does not match its file type"

iOS photos are HEIC by default. When picked in mobile Chrome, the file is either sent as `image/heic` (→ L68) or carries a `.jpeg` name while the bytes are HEIF (→ L82 or L85). Any of these → 415 → the generic toast. This matches the live 415 bursts.

## Suggested fixes (debug only — I applied nothing)

### Fix A — Code (E1), primary. Requires redeploy.
Support iPhone HEIC uploads: accept `image/heic`/`image/heif` and transcode to JPEG/WebP server-side (e.g. pillow-heif) in `backend/routers/media.py`, OR convert HEIC→JPEG client-side before POST. This is the real cause for this user.

### Fix B — Code (E1), UX. Requires redeploy.
Fix the misleading toast in `ImageManager.tsx`: surface the backend's 415 `detail` (e.g. "Upload a JPG, PNG or WebP image" / "format does not match its file type") instead of the generic "could not be uploaded", so this stops looking like a network error. Note the native picker's `accept="image/jpeg,image/png,image/webp"` does not restrict drag-drop and does not stop iOS handing over HEIC.

### User workaround (immediate, no redeploy)
On the iPhone set Camera → Formats → "Most Compatible" (shoots JPEG), or convert the existing HEIC photo to JPG/PNG/WebP before uploading. The upload endpoint itself is working on safyra.co (other photos return 201).
