# RCA — safyra.co shows no products / no collections / changed design

## Problem statement
After going live, https://safyra.co shows no products, no collections, and a changed
(fallback) design. Preview had 4 approved products, 8 categories, 3 collections, the
premium SAFYRA design, working Admin/PayU/GST and GridFS media.

## Verdict on the three questions asked
1. **Is safyra.co routing to Emergent or still to Shopify/Wix?**
   → Routing is CORRECT and fully on the Emergent deployment. Nothing Shopify/Wix.
2. **Is the deployed frontend the correct current build?**
   → YES. The live build is the current SAFYRA build.
3. **Is production Mongo/DB_NAME bound to an empty DB / did data fail to migrate?**
   → NO. DB is correctly bound and fully populated. Data migrated fine.

The real cause is a **backend runtime crash on every catalog endpoint** — the storefront
receives HTTP 500 for products, collections and homepage content, so it renders an empty
fallback state.

## Evidence
- **Routing (healthy):** `list_domains` → `safyra.co` and `www.safyra.co` both
  verified=true, provider=cloudflare, ssl_status=active. `check_domain_status` → both
  linked=true (live DNS points at us). Traffic is served by the Emergent k8s deployment,
  not Shopify/Wix.
- **Build (correct):** `preview_health_check /` on https://lucknowi-craft.emergent.host →
  200, HTML is the SAFYRA Chikankari build (og:site_name "SAFYRA CHIKANKARI", SAFYRA
  description, app favicons). Frontend bundle is the current build.
- **DB binding + data (correct, NOT empty):** `mongo_query` resolved db_name =
  `lucknowi-craft-app`, 22 collections. Counts:
  - products = **4** (the four approved: Vaaya Pure Kota Doria Anarkali, Luxury Nazakat
    Collection, Aira Pure Kota Doria Angrakha, Sang-e-Mar-Mar — Rose Edition)
  - catalog_groups = **11** (= 8 categories + 3 collections)
  - site_content = 1, store_settings = 1
  Migration succeeded; MONGO_URL/DB_NAME are bound to the correct, populated database.
- **Actual fault (proven):** `preview_health_check /api/products` → **500 Internal Server
  Error**. `fetch_app_logs` shows the same exception on every data route:
  ```
  RuntimeError: Task ... got Future <Future pending> attached to a different loop
    File "/app/backend/routers/products.py", line 40, in _ensure_catalog
      if await db.products.count_documents({}) == 0:
    File "/app/backend/routers/catalog_groups.py", line 36, in _ensure_groups
      products = await db.products.find({}).sort("created_at", 1).to_list(1000)
    File "/app/backend/routers/homepage.py", line 14, in _get_or_create
      document = await db.site_content.find_one({"id": "homepage"})
  ```
  So `/api/products`, `/api/catalog-groups` and `/api/homepage` all 500.

## Root cause
`backend/lib/db.py` creates the Mongo client at **module-import time**:
```python
# backend/lib/db.py
mongo_url = os.environ["MONGO_URL"]
client = AsyncIOMotorClient(mongo_url)        # <-- line 14, created at import
db = client[os.environ["DB_NAME"]]
```
A Motor `AsyncIOMotorClient` binds its internal futures to the event loop that is running
when it is created. Because it is instantiated at import, it binds to the import-time loop,
but under the production uvicorn runtime the request handlers execute on a **different**
event loop. Every awaited DB operation then raises
`RuntimeError: got Future <Future pending> attached to a different loop`, which surfaces as
HTTP 500 on all data endpoints.

This passed in preview and in iteration_30 tests because the dev/test runner executed within
the same event loop that imported the module, so the loop mismatch never occurred. It only
manifests in the production serving process. MONGO_URL/DB_NAME are correct — this is purely
how/when the client object is constructed.

## "Design changed" explanation
`/api/homepage` (site_content) 500s, so the storefront cannot load the SAFYRA homepage
content document and renders its default/empty fallback layout — perceived as a changed
design. It will restore once the endpoint returns 200.

## Corrective action (Code fix — E1)
Create the Motor client **inside the running event loop** rather than at import, so it binds
to the loop that serves requests. Any of:
- Instantiate the client in a FastAPI startup/lifespan handler and assign `client`/`db`
  there, or
- Lazily create the client on first use (function/dependency that returns a client built on
  the current loop), or
- Pass the current loop explicitly, e.g. `AsyncIOMotorClient(mongo_url, io_loop=asyncio.get_event_loop())`
  created at startup.
Keep `ensure_indexes()` and the `_ensure_catalog`/`_ensure_groups` bootstrap calls using the
loop-bound client. Then redeploy.

No DNS change, no data change, no tier change, no secret change required. Data and routing
are already correct; the single fix is the DB client initialization in `backend/lib/db.py`.

## Note (minor, not the cause)
`GET /health` returns 404 in logs — harmless here (the deploy health check still passed),
but E1 may want to add a `/health` route for cleaner probes.
